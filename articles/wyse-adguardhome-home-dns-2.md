[前編](https://zenn.dev/yowahada/articles/wyse-adguardhome-home-dns)では、余っていた小型PC（Dell Wyse 3040）にAdGuardHomeを入れ、家の中のDNSサーバとして動かしました。広告やトラッカーのドメインを聞かれると、どこにもつながらない住所を返して止める仕組みです。

ただ、DNSサーバは置いただけでは使われません。後編では、家のスマホやPCにこのDNSサーバを使ってもらいます。前編の冒頭で紹介した、ルーターが配るDNSの設定を書き換える攻撃は、まさにこの「端末がどのDNSサーバを使うか」を狙ったものでした。

そのあと、記事を見直していて見つけたIPv6の落とし穴の話をします。最後に、DNSサーバが止まったらすぐ気づけるよう、毎朝の点検を組みます。

## 家の端末に使ってもらう

### 置いただけでは、どの端末も使わない

AdGuardHomeが動いても、端末がそこに問い合わせなければ広告は止まりません。端末は、教えられたDNSサーバにだけ問い合わせるからです。

### DHCPとDNSは別の仕組み

端末がWi-Fiなどにつながると、ルーターのDHCPという仕組みが、その端末にIPアドレスを割り当てます。このとき、DHCPは「このDNSサーバを使ってください」という情報も一緒に配ります。

つまり、DHCPは端末の設定を配る係で、DNSは名前を調べる係です。家中の端末にAdGuardHomeを使ってもらうには、本来はルーターのDHCPで「DNSは<WyseのIP>」と配るのが一番楽です。

### うちのルーターでは、配るDNSを変えられなかった

ところが、**ソフトバンクの光BBユニットでは、配るDNSサーバを変えられません**。DHCPの設定にあるのは「本機IP変更」「割当範囲」「固定割当（8個まで）」の3項目だけで、配るDNSサーバを入れる欄がありません。探し方の問題ではなく、その機能がありません。

取れる道は2つありました。1つは、端末ごとにDNSを手で設定する方法です。もう1つは、AdGuardHome自身をDHCPサーバにして、光BBユニットの代わりに設定を配らせる方法です。

| | 端末ごとに手動設定 | AdGuardHomeをDHCPに |
|---|---|---|
| 効く範囲 | 設定した端末だけ | 家中すべて |
| DNSを設定できない機器（TV等） | 効かない | 効く |
| Wyseが止まったとき | その端末の名前解決だけ止まる | **家中がIPを取れず全断** |

前者の、端末ごとに手で設定する方法を選びました。光BBユニットのDHCPは止められないので、後者だとDHCPサーバが2台あることになります。どちらが答えるかが毎回変わり、故障したときに原因を切り分けにくくなるからです。

### WyseのIPアドレスを固定する

端末ごとの設定では、各端末にWyseのIPアドレスを直接書き込みます。そのため、WyseのIPアドレスが変わると困ります。光BBユニットの「固定割当」で、Wyseにはいつも同じIPアドレスを割り当てるようにしました。

:::message alert
各端末はWyseのIPアドレスを直接指しているので、**IPアドレスが変わると、設定した端末がすべて名前を引けなくなります**。固定は必須です。
:::

### 端末側の設定

iPhoneは「Wi-Fiの詳細 → DNSを構成 → 手動」で、DNSだけを差し替えられます。

手元のAndroidでは、DNSだけを変える項目がなく、IP設定を「静的」にしてIPアドレスとDNSを手で入れる必要がありました。「プライベートDNS」という項目もありますが、これは暗号化したDNS（DoT）用で、ホスト名を入れる欄です。手元の機種では、家の中のIPアドレスを指定する使い方はできませんでした。

:::message alert
セカンダリDNS（DNS 2）に `8.8.8.8` などを入れてはいけません。AdGuardHomeがブロックしたドメインを、端末がそちらに聞き直してしまい、**ブロックがすり抜ける**ことがあります。予備の問い合わせ先がない不安より、全部の問い合わせを確実にAdGuardHomeに通すほうを優先して、空欄にしました。
:::

## IPv6で家の外に出ていたかもしれない

公開前に記事を見直していて、もう1つ問題を見つけました。前編の手順6の初期設定ウィザードで「全インターフェイス」を選んだため、AdGuardHomeのDNS（53番）と管理画面（80番）は、IPv4だけでなくIPv6のアドレスでも受け付けていました。

IPv4では、家の機器はルーターの内側にあり、外からは直接届きません。一方、IPv6では家の機器一つ一つにインターネットから届くアドレス（グローバルアドレス）が付きます。外から届くかどうかは、ルーターのIPv6のフィルタで決まり、その既定の動きは機種によって違います。Wyseにはファイアウォールを入れておらず、AdGuardHomeの「問い合わせを受け付ける端末」の設定も空（だれでも可）のままでした。

光BBユニットのフィルタが外からの通信を止めていたかは、家の中からは確かめられませんでした。もし届いていたら、AdGuardHomeはだれでも使えるDNSサーバ（オープンリゾルバ）として、DDoS攻撃の踏み台に使われるおそれがありました。管理画面のログイン画面もインターネットから見えていたことになります。

家の端末はどれもIPv4でWyseを指定しているので、IPv6で受け付ける必要はありません。そこで、受け付けるアドレスをWyseのIPv4アドレスとWyse自身（`127.0.0.1`）だけに絞りました。設定の手順は、[前編](https://zenn.dev/yowahada/articles/wyse-adguardhome-home-dns)の手順8にまとめてあります。

:::message alert
IPv6が使える回線では、「ルーターの内側だから外から届かない」という前提は成り立たないことがあります。家の中に置くサーバも、受け付けるアドレスを必要な範囲に絞っておきます。
:::

## 運用と監視

DNSサーバは止まると家中に影響が出るのに、止まっても気づきにくい機器です。systemdのタイマー（決まった時刻にプログラムを動かす仕組み）で、点検を毎日回しています。点検のプログラムは、Pythonの標準ライブラリだけで書いていて、追加のインストールは要りません。

### 毎朝のヘルスレポート

毎朝8時に、機体の状態をLINEに送っています。正常なときは数行で、異常があるときだけ詳しく書きます。見ている項目は次のとおりです。

| 項目 | なぜ見るか |
|---|---|
| ディスクの空き | eMMCが8GBしかない |
| メモリの空き（200MB未満で警告） | 2GBしかない |
| CPU温度（80℃超で警告） | ファンがなく熱がこもる |
| eMMCの消耗度 | 書き込める回数に寿命がある |
| 再起動の有無 | 停電やクラッシュに気づくため |

レポートが届かないこと自体も異常のサインになります。Wyseが止まっていれば、レポートは来ないからです。毎朝届くかどうかで、死活監視も兼ねています。

### DNSが本当に答えるかで判定する

AdGuardHomeが動いているかは、`systemctl is-active`（サービスが動作中かを答えるコマンド）では判定していません。プロセスが動いていても名前解決ができなくなったことが、実際にあったからです。点検のプログラムが自分でDNSの問い合わせを組み立てて `127.0.0.1:53` に送り、答えが返ってくるかで判定しています。

### eMMCの消耗度を読む

eMMCは書き込みを繰り返すと少しずつ劣化します。消耗度は次のコマンドで読めます。

```bash
cat /sys/block/mmcblk0/device/life_time   # → 0x01 0x01 なら 0-10%
```

2つの値は、eMMCの中の2つの領域それぞれの消耗度です。値が `n` なら、消耗が (n−1)×10〜n×10% の範囲という意味です。`0x01` は0〜10%で、まだほとんど減っていません。中古のシンクライアントを使い回すときは、地味ですが見ておきたい数字です。

### ついでに動かしているもの

本題とは関係ありませんが、常時起動の機体があるついでに、平日の夜に監視している株の値動きを調べてLINEに送るジョブも動かしています。

## まとめ（後編）

- **ルーターが配るDNSを変えられるかを、最初に確かめます。** 変えられないと、端末ごとに設定するしかなく、TVのように設定できない機器では広告を止められません。
- **セカンダリDNSを足すと、ブロックがすり抜けることがあります。** 冗長にしたつもりで、守りに穴が開きます。
- **IPv6では「ルーターの内側だから安全」とは限りません。** 受け付けるアドレスは、必要な範囲に絞ります。
- **死活監視は、プロセスが動いているかではなく、実際に名前を引けるかで見ます。**

次は、この家庭内LANで自分のスマホの通信を実際にMITM（通信の途中に割り込んで中身を見る手法）して、「暗号化しても宛先は漏れる」を確かめる記事を書く予定です。自分の端末と自分のネットワークに限って行い、最後は対策で締めます。

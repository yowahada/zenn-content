**「軽量ディストリを選べば非力なマシンでも動くだろう」と思い込んで、インストールに2回失敗しました。**

この記事は、余っていた小型PC（Dell Wyse 3040）にAdGuardHomeという広告ブロックのソフトを入れ、家のスマホやPCの広告とトラッカーをまとめて止めた記録です。トラッカーは、閲覧履歴を集めるために広告会社などが仕込んでいる通信のことです。

できあがった環境では、スマホとPCの広告が端末側のアプリなしで消えました。メモリ2GBの機体で、AdGuardHomeが使うメモリは約100MBです。毎朝、機体の点検結果がLINEに届くようにもしました。

役に立ちそうな学びは3つあります。小型PCで最初に気にするべきだったのはCPUではなくディスク容量だったこと。家のルーターが「どのDNSサーバを使うか」を端末に配れないときの対処。そして、記事を見直していて見つけた、IPv6で管理画面とDNSが家の外に出ていたかもしれない問題です。

:::message
**対象読者**：余ったx86の小型機（シンクライアント等）がある人。家中の広告やトラッカーをまとめて止めたい人。
**必要なもの**：常時起動できる小型機、OSを書き込むUSBメモリ、家庭内LAN。Linuxの基本操作とSSHが分かると楽です。
:::

## 完成した環境

![自宅LANの構成：端末のDNSはWyse(AdGuardHome)へ、通常の通信はGW経由](/images/home-lan-normal.png)
*端末のDNSだけをWyse(AdGuardHome)に向け、広告・トラッカーをブロックする。管理はMacからSSH。*

図の線は3種類あります。①の線はDNSの問い合わせで、スマホやMacから真ん中のWyseに届き、Wyseからインターネット上のDNSサーバに転送されます。もう1種類はWebページそのものの通信で、Wyseを通らずにルーター（光BBユニット）から直接インターネットに出ます。②の線は、MacからSSHでWyseを管理する通信です。

つまり、Wyseが関わるのは「どのサーバにつなぐか」を調べる段階だけです。動画や画像などの重い通信はWyseを通らないので、非力な機体でも家全体が遅くなりません。

使っている資源は次のとおりです。メモリは導入直後で77MB、1か月あまり動かした今は約100MBで、2GBのうちのごく一部です。ディスクは導入直後で3.5GBを使い、空きは2.8GBでした。CPUやメモリには余裕がある一方、ディスクの空きは少なく、この少なさが後で書く失敗の原因になりました。

## 仕組み：DNSの段階で広告を止める

### DNSは「名前から住所を調べる仕組み」

スマホでWebサイトを開くとき、端末はまず `example.com` のような名前を、`203.0.113.10` のような数字の住所（IPアドレス）に置き換えます。この置き換えを担当するのがDNSサーバです。電話帳で名前から電話番号を引くのに近い動きです。

広告も同じで、ページの中の広告を表示する前に、端末は広告配信サーバの名前をDNSで調べています。

### AdGuardHomeは広告の名前にだけ「ない」と答える

AdGuardHomeは、家の中に置くDNSサーバのソフトウェアです。広告やトラッカーのドメインの一覧を持っていて、一覧にある名前を聞かれると、どこにもつながらない住所 `0.0.0.0` を返します。端末は広告配信サーバにつながらないので、広告が表示されません。この方式を「DNSシンクホール」と呼びます。

端末側はDNSの問い合わせ先をAdGuardHomeに変えるだけで済みます。アプリを入れられない機器でも、DNSの設定さえ変えられれば効きます。

### 普通のサイトは「上流DNS」に聞いてもらう

広告ではない普通のサイトを開くとき、AdGuardHomeは自分では住所を知らないので、インターネット上の別のDNSサーバに問い合わせて答えを受け取り、端末に返します。この問い合わせ先を「上流DNS」と呼びます。

今回は上流DNSとの通信をDoH（DNS over HTTPS）にしました。DoHは、DNSの問い合わせをWebと同じHTTPSで暗号化して送る方式です。これで、家からどんな名前を問い合わせたかは、回線事業者（ISP）から見えなくなります。

ただし、見えなくなるのはDNSの問い合わせだけです。その後に実際につなぐ相手のIPアドレスなどは、今までどおり回線事業者から見えます。DoHは通信全体を隠す仕組みではありません。

## なぜこの構成にしたか

**Wyse 3040**：ファンがないので静かで、消費電力も小さく、24時間つけっぱなしに向いています。何より家で余っていました。弱点は、保存領域がeMMC（スマホなどに使われる基板直付けのフラッシュメモリ）の8GBしかないことです。

**Ubuntu Server（minimized）**：画面表示の仕組み（デスクトップ環境）を持たない、最小構成のサーバ版です。DNSサーバに画面は要らず、8GBのディスクに収まるのがこれでした。ここに落ち着くまでに2回失敗しています（後述）。

**AdGuardHome**：1つの実行ファイル（単一バイナリ）で動き、自動更新の仕組みも持っています。同じ目的のPi-holeは複数のソフト（dnsmasq等）を組み合わせて動くので、動かすものが1つで済むAdGuardHomeのほうがこの機体に向いていました。

**Dockerを使わず直接インストール**：Dockerは、ソフトを専用の箱（コンテナ）に入れて動かす仕組みです。今回は使わず、直接インストールしました。理由は、ディスクが8GBしかないうえに、Docker自体にも追加のディスクとメモリが必要だからです。

| | ディスク | メモリ |
|---|---|---|
| 直接インストール | 約40MB | 約50〜100MB（実測77MB） |
| Docker | 約400〜500MB＋イメージ60MB | 上記＋dockerd常駐 100〜200MB |

実測値は直接インストールしたときのメモリ77MBだけで、ほかは見積もりです。空き2.8GB、メモリ2GBの機体では、Dockerのぶんの上乗せが相対的に重くなります。AdGuardHomeは単一バイナリで自動更新も持っているので、コンテナに入れる利点（環境の分離や更新のしやすさ）も小さいと判断しました。

## 構築手順

ここからの作業は、OSを入れたWyseにMacからSSHで接続して行いました。

### 1. タイムゾーンを日本時間にする

初期状態はUTC（世界標準時）なので、そのままだとAdGuardHomeの問い合わせ記録の時刻が9時間ずれます。最初に直しておきます。

```bash
sudo timedatectl set-timezone Asia/Tokyo
```

### 2. AdGuardHomeを取得して配置する

**目的**：AdGuardHomeの実行ファイル一式を `/opt/AdGuardHome` に置きます。

公式は `curl | sh`（ダウンロードしたスクリプトをそのまま実行する方法）を案内しています。今回は、何が置かれるかを自分で把握したかったので、GitHubのリリースから直接取得して手で配置しました。

```bash
URL=$(curl -sL https://api.github.com/repos/AdguardTeam/AdGuardHome/releases/latest \
  | grep -o 'https://[^"]*AdGuardHome_linux_amd64.tar.gz' | head -1)
cd /tmp
curl -sL -o AdGuardHome.tar.gz "$URL"
tar xzf AdGuardHome.tar.gz
sudo mv /tmp/AdGuardHome /opt/AdGuardHome
```

1〜2行目で最新版のダウンロードURLを調べ、残りの行でダウンロード、展開、移動をしています。

**確認**：実行ファイル `AdGuardHome` が置かれていれば成功です。

```bash
ls /opt/AdGuardHome
```

### 3. ポート53を空ける（ここが一番大事）

**何が問題か**：DNSサーバは、決まった受付窓口（ポート53番）で問い合わせを受けます。ところがUbuntuでは、`systemd-resolved` という名前解決の仕組みが最初から53番を使っています。このままではAdGuardHomeが53番を使えません。

**目的**：`systemd-resolved` に53番を手放させつつ、Wyse自身の名前解決は続けられるようにします。

```bash
sudo cp /etc/systemd/resolved.conf /etc/systemd/resolved.conf.bak
echo "DNSStubListener=no" | sudo tee -a /etc/systemd/resolved.conf
sudo ln -sf /run/systemd/resolve/resolv.conf /etc/resolv.conf
sudo systemctl restart systemd-resolved
```

1行目は設定ファイルのバックアップです。2行目の `DNSStubListener=no` で、`systemd-resolved` が53番で待ち受けるのをやめさせます。3行目では、Wyse自身が名前を調べるときの参照先 `/etc/resolv.conf` を、実際の上流DNSが書かれたファイル `/run/systemd/resolve/resolv.conf` に付け替えます。4行目で設定を反映します。

:::message alert
`DNSStubListener=no` **だけ**で終えると、`systemd-resolved` は53番を手放しますが、`/etc/resolv.conf` は `nameserver 127.0.0.53` を指したままになります。そこにはもう誰もいないので、**Wyse自身の名前解決が止まります**。3行目の付け替えまでやって初めて成り立ちます。
:::

**確認**：1行目で53番を使っているプログラムが表示されなければ、53番は空いています。2行目で `github.com` の住所が表示されれば、Wyse自身の名前解決も動いています。

```bash
sudo ss -tulnp | grep ':53 '
getent hosts github.com
```

### 4. サービスとして登録する

**目的**：Wyseを起動したら、AdGuardHomeも自動で動くようにします。

```bash
cd /opt/AdGuardHome
sudo ./AdGuardHome -s install
```

`-s install` を付けると、systemd（Linuxでサービスを管理する仕組み）への登録、自動起動の有効化、起動までを一度にやってくれます。

**確認**：`Active: active (running)` と表示されれば動いています。

```bash
systemctl status AdGuardHome
```

### 5. スリープさせない

**目的**：DNSサーバが眠ると、家中の名前解決が止まります。スリープ系の動作を4つまとめて無効にします。

```bash
sudo systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target
```

`mask` すると、それぞれの動作が `/dev/null`（何もしない特殊なファイル）に付け替えられ、どこから呼ばれても起動しなくなります。何もしないままだと、ACPIイベント（電源まわりのハードウェアからの通知）などから呼ばれる可能性が残ります。

:::message
電源ボタンは無効にしていません（`logind.conf` は初期設定のまま）。物理的に安全に止める手段は残しておきたかったからです。
:::

### 6. 初期設定ウィザードを済ませる

ブラウザで `http://<WyseのIP>:3000` を開くと、AdGuardHomeの初期設定画面が出ます。

| 項目 | 設定値 |
|---|---|
| 管理用ウェブUI | 全インターフェイス / ポート 80 |
| DNSサーバ | 全インターフェイス / ポート 53 |
| 管理者アカウント | 任意 |

設定が終わると、管理画面は `:3000` の付かないURLに変わります。

ここで選んだ「全インターフェイス」は、Wyseが持つすべてのアドレスで受け付ける、という意味です。この選び方には落とし穴があり、1か月あまり後に直しました（「IPv6で家の外に出ていたかもしれない」で後述）。

:::message alert
管理画面は**家庭内LANだけで使う**前提です。ルーターのポート開放などで**インターネット側に絶対に出さない**でください。管理者パスワードも強いものにします。
:::

### 7. 上流DNSにDoHを設定する

管理画面の上流DNSの欄に、Quad9のDoHのURLを入れました。

```
https://dns10.quad9.net/dns-query
```

:::message
非力な機体では、DoHの暗号化（TLS）の処理が負荷になるかもしれません。測ってはいませんが、体感が重ければ暗号化しない普通のDNSに戻すのも選択肢です。プライバシーと速度のどちらを取るか、の判断になります。
:::

## 失敗談

### Lubuntuで2回インストールに失敗した

**やろうとしたこと**：非力なマシンの再生といえば軽量ディストリ、と考えて、最初にLubuntu 24.04を選びました。LubuntuはLXQtという軽い画面表示の仕組みを使ったUbuntuの仲間です。

**何が起きたか**：1回目は通常のインストール（Normal Installation）で、終盤に `外部のコマンドがエラーで停止しました` と出て中断しました。2回目は最小構成（Minimal Installation）にし、追加のダウンロードも切って再挑戦しましたが、同じ場所で止まりました。今度はエラーの全文が読めました。

```
コマンド update-initramfs が終了コード 1 で終了しました。
cpio: write error: No space left on device
E: mkinitramfs failure uncompressed cpio 2
```

**エラーから分かったこと**：`No space left on device` は「ディスクに空きがない」という意味です。パッケージの展開までは済んでいて、最後のinitrdを作る段階で容量が尽きていました。initrdは、起動の最初に読み込まれる小さな起動用ファイルで、作る途中で一時的に作業場所を使います。デスクトップ環境を載せる前提では、削れるところを削っても入りきりませんでした。

**根本原因**：Lubuntuがうたう「軽さ」は、メモリとCPUの負荷が軽いという意味でした。**ディスク使用量が小さいという意味ではありません。** Wyse 3040のボトルネックはディスクのほうでした。

**どう解決したか**：DNSサーバに画面は要らない、という当たり前に立ち返り、Ubuntu Server（minimized）を入れ直したら、何事もなく最後まで進みました。

| OS | 結果 | 備考 |
|---|---|---|
| Lubuntu 24.04 Normal | 失敗 | initrd作成時に容量不足 |
| Lubuntu 24.04 Minimal | 失敗 | デスクトップ環境だけでも入らない |
| Ubuntu Server 24.04.3 minimized | 成功 | 導入後 3.5G使用 / 2.8G空き |

インストール時は次のように選びました。

- Installation Mode は Ubuntu Server (minimized)
- ストレージはディスク全体を使い、LVMは無効にしました。LVMはディスクを柔軟に分けるための仕組みですが、数GBの単一用途の機体では利点がありません。全容量がrootに割り当てられない事態や、起動用ファイルが大きくなるのも避けたかったからです
- Install OpenSSH server にチェックを入れました。以降の作業をすべてMacから行うために必須です

:::message
**次に同じことをするなら**：「軽量ディストリ」はメモリとCPUの話で、ディスクの話とは限りません。eMMC 8GB級の機体を再生するなら、デスクトップ版は最初から選択肢に入れず、用途がサーバなら素直にServer版を選びます。
:::

### インストールUSBを挿したまま再起動したら止まった

**何が起きたか**：インストール後の初回起動が `cloud-init ... running 'init-local'` の表示で完全に止まりました。cloud-initは、初回起動時に設定を読み込んで機体を整える仕組みです。

**原因と解決**：cloud-initが設定の供給元を探すとき、挿しっぱなしのインストールUSBを候補と見なして待ち続けていました。USBを抜いて再起動したら、一発で通りました。

## 家の端末に使ってもらう

### 置いただけでは、どの端末も使わない

AdGuardHomeが動いても、端末がそこに問い合わせなければ広告は止まりません。端末は、教えられたDNSサーバにだけ問い合わせるからです。

### DHCPとDNSは別の仕組み

端末がWi-Fiなどにつながると、ルーターのDHCPという仕組みが、その端末にIPアドレスを割り当てます。このとき、DHCPは「このDNSサーバを使ってください」という情報も一緒に配ります。

つまり、DHCPは端末の設定を配る係で、DNSは名前を調べる係です。家中の端末にAdGuardHomeを使ってもらうには、本来はルーターのDHCPで「DNSは<WyseのIP>」と配るのが一番楽です。

### うちのルーターでは、配るDNSを変えられなかった

ところが、**ソフトバンクの光BBユニットはこれができません**。DHCPの設定にあるのは「本機IP変更」「割当範囲」「固定割当（8個まで）」の3項目だけで、配るDNSサーバを入れる欄がありません。探し方の問題ではなく、その機能がありません。

取れる道は2つありました。1つは、端末ごとにDNSを手で設定する方法です。もう1つは、AdGuardHome自身をDHCPサーバにして、光BBユニットの代わりに設定を配らせる方法です。

| | 端末ごとに手動設定 | AdGuardHomeをDHCPに |
|---|---|---|
| 効く範囲 | 設定した端末だけ | 家中すべて |
| DNSを設定できない機器（TV等） | 効かない | 効く |
| Wyseが止まったとき | その端末の名前解決だけ止まる | **家中がIPを取れず全断** |

前者の、端末ごとに手で設定する方法を選びました。光BBユニットのDHCPは止められないので、後者だとDHCPサーバが2台あることになります。どちらが答えるかが毎回変わり、故障したときに原因を切り分けにくくなるからです。

### WyseのIPアドレスを固定する

端末ごとの設定では、各端末にWyseのIPアドレスを直接書き込みます。そのため、WyseのIPアドレスが変わると困ります。光BBユニットの「固定割当」で、Wyseにはいつも同じIPアドレスを割り当てるようにしました。

:::message alert
各端末はWyseのIPアドレスを直接指しているので、**IPアドレスが変わると、設定した端末がすべて名前を引けなくなります**。固定は必須です。
:::

### 端末側の設定

iPhoneは「Wi-Fiの詳細 → DNSを構成 → 手動」で、DNSだけを差し替えられます。

手元のAndroidでは、DNSだけを変える項目がなく、IP設定を「静的」にしてIPアドレスとDNSを手で入れる必要がありました。「プライベートDNS」という項目もありますが、これは暗号化したDNS（DoT）用で、ホスト名しか受け付けず、家の中のIPアドレスは指定できません。

:::message alert
セカンダリDNS（DNS 2）に `8.8.8.8` などを入れてはいけません。AdGuardHomeがブロックしたドメインを、端末がそちらに聞き直してしまい、**ブロックがすり抜ける**ことがあります。予備の問い合わせ先がない不安より、全部の問い合わせを確実にAdGuardHomeに通すほうを優先して、空欄にしました。
:::

## IPv6で家の外に出ていたかもしれない

この記事を公開前に見直していて、もう1つ問題を見つけました。初期設定ウィザードで「全インターフェイス」を選んだため、AdGuardHomeのDNS（53番）と管理画面（80番）は、IPv4だけでなくIPv6のアドレスでも受け付けていました。

IPv4では、家の機器はルーターの内側にあり、外からは直接届きません。一方、IPv6では家の機器一つ一つにインターネットから届くアドレス（グローバルアドレス）が付きます。外から届くかどうかは、ルーターのIPv6のフィルタだけで決まります。Wyseにはファイアウォールを入れておらず、AdGuardHomeの「問い合わせを受け付ける端末」の設定も空（だれでも可）のままでした。

光BBユニットのフィルタが外からの通信を止めていたかは、家の中からは確かめられませんでした。もし届いていたら、AdGuardHomeはだれでも使えるDNSサーバ（オープンリゾルバ）として、DDoS攻撃の踏み台に使われるおそれがありました。管理画面のログイン画面もインターネットから見えていたことになります。

家の端末はどれもIPv4でWyseを指定しているので、IPv6で受け付ける必要はありません。そこで、受け付けるアドレスをWyseのIPv4アドレスと、Wyse自身（`127.0.0.1`）だけに絞りました。設定ファイル `/opt/AdGuardHome/AdGuardHome.yaml` の2か所を、バックアップを取ってから書き換えます。

```yaml
# DNSを受け付けるアドレス（dns: の中）
  bind_hosts:
    - 127.0.0.1
    - <WyseのIP>

# 管理画面のアドレス（http: の中）
  address: <WyseのIP>:80
```

`127.0.0.1` を残したのは、後で書く毎朝の点検が、Wyseの中から `127.0.0.1` のDNSに問い合わせて動作を確かめているからです。

書き換えたら `sudo systemctl restart AdGuardHome` で再起動します。再起動の数秒間は、家の名前解決が止まります。

**確認**：53番と80番の行に、IPv4のアドレスだけが並べば成功です。`*:53` や `[::]:53` のような、すべてのアドレスを表す行が残っていなければ大丈夫です。

```bash
sudo ss -tulnp | grep AdGuardHome
```

:::message alert
IPv6が使える回線では、「ルーターの内側だから外から届かない」という前提は成り立たないことがあります。家の中に置くサーバも、受け付けるアドレスを必要な範囲に絞っておきます。
:::

## 運用と監視

DNSサーバは止まると家中に影響が出るのに、止まっても気づきにくい機器です。systemdのタイマー（決まった時刻にプログラムを動かす仕組み）で、点検を毎日回しています。点検のプログラムは、Pythonの標準ライブラリだけで書いていて、追加のインストールは要りません。

### 毎朝のヘルスレポート

毎朝8時に、機体の状態をLINEに送っています。正常なときは数行で、異常があるときだけ詳しく書きます。見ている項目は次のとおりです。

| 項目 | なぜ見るか |
|---|---|
| ディスクの空き | eMMCが8GBしかない |
| メモリの空き（200MB未満で警告） | 2GBしかない |
| CPU温度（80℃超で警告） | ファンがなく熱がこもる |
| eMMCの消耗度 | 書き込める回数に寿命がある |
| 再起動の有無 | 停電やクラッシュに気づくため |

レポートが届かないこと自体も異常のサインになります。Wyseが止まっていれば、レポートは来ないからです。毎朝届くかどうかで、死活監視も兼ねています。

### DNSが本当に答えるかで判定する

AdGuardHomeが動いているかは、`systemctl is-active`（サービスが動作中かを答えるコマンド）では判定していません。プロセスが動いていても名前解決ができなくなったことが、実際にあったからです。点検のプログラムが自分でDNSの問い合わせを組み立てて `127.0.0.1:53` に送り、答えが返ってくるかで判定しています。

### eMMCの消耗度を読む

eMMCは書き込みを繰り返すと少しずつ劣化します。消耗度は次のコマンドで読めます。

```bash
cat /sys/block/mmcblk0/device/life_time   # → 0x01 0x01 なら 0-10%
```

2つの値は、eMMCの中の2つの領域それぞれの消耗度です。値が `n` なら、消耗が (n−1)×10〜n×10% の範囲という意味です。`0x01` は0〜10%で、まだほとんど減っていません。中古のシンクライアントを使い回すときは、地味ですが見ておきたい数字です。

### ついでに動かしているもの

本題とは関係ありませんが、常時起動の機体があるついでに、平日の夜に監視している株の値動きを調べてLINEに送るジョブも動かしています。

## まとめ：次に小型機でサーバを作る人へ

- **小型機の再生で最初に見るのは、CPUよりディスク容量です。** 「軽量」はメモリとCPUの話のことが多く、eMMC 8GB級ではデスクトップ版のOSが入りませんでした。
- **ルーターが配るDNSを変えられるかを、最初に確かめます。** 変えられないと、端末ごとに設定するしかなく、TVのように設定できない機器には効きません。
- **セカンダリDNSを足すと、ブロックがすり抜けることがあります。** 冗長にしたつもりで、守りに穴が開きます。
- **IPv6では「ルーターの内側だから安全」とは限りません。** 受け付けるアドレスは、必要な範囲に絞ります。
- **死活監視は、プロセスが動いているかではなく、実際に名前を引けるかで見ます。**

次は、この家庭内LANで自分のスマホの通信を実際にMITM（通信の途中に割り込んで中身を見る手法）して、「暗号化しても宛先は漏れる」を確かめる記事を書く予定です。自分の端末と自分のネットワークに限って行い、最後は対策で締めます。

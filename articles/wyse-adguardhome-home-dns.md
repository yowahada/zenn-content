2026年4月、英国のNCSC（国家サイバーセキュリティセンター）や米国のFBIなどが、ロシア軍の情報機関に属する攻撃者が世界中の家庭用・小規模オフィス用ルーターを乗っ取っていたと発表しました（[FBIなどの注意喚起](https://www.ic3.gov/PSA/2026/PSA260407)）。攻撃者はルーターが配るDNSの設定を書き換えていて、つながっているPCやスマホは、その設定をそのまま受け取って攻撃者のDNSサーバに問い合わせていました。攻撃者は特定のサイトにだけ偽の答えを返し、証明書の警告を無視して進んだ利用者の通信から、パスワードなどを盗んでいたそうです。

国内でも2026年7月、総務省・警察庁・NICTが、家庭のルーターやIoT機器が知らないうちに犯罪の通信の中継に使われる「レジデンシャルプロキシ」について資料を公表しました（[NICTの発表](https://www.nict.go.jp/press/2026/07/21-1.html)）。2024年のネットバンキングの不正送金のうち、件数で約44%にこの仕組みが使われていたそうです。

自宅のネットワークも、狙われる前提で考えないといけない。そう思い、まず家の端末がどのDNSサーバに問い合わせているかを、自分で管理できるようにしました。

この記事は、余っていた小型PC（Dell Wyse 3040）にAdGuardHomeというDNSサーバのソフトを入れ、家のスマホやPCの広告とトラッカーをまとめて止めた記録です。トラッカーは、閲覧履歴を集めるために広告会社などが仕込んでいる通信のことです。

できあがった環境では、スマホとPCの広告が端末側のアプリなしで消えました。メモリ2GBの機体で、AdGuardHomeが使うメモリは約100MBです。毎朝、機体の点検結果がLINEに届くようにもしました。

記事は2回に分けました。前編のこの記事では、WyseをDNSサーバとして動かすところまでを書きます。[後編](https://zenn.dev/yowahada/articles/wyse-adguardhome-home-dns-2)では、家の端末につないで、守りを固めます。<!-- 後編のリンクは公開後に確かめる -->

:::message
**対象読者**：余ったx86の小型機（シンクライアント等）がある人。家中の広告やトラッカーをまとめて止めたい人。
**必要なもの**：常時起動できる小型機、OSを書き込むUSBメモリ、家庭内LAN。Linuxの基本操作とSSHが分かると楽です。
:::

## 完成した環境

![自宅LANの構成：端末のDNSはWyse(AdGuardHome)へ、通常の通信はGW経由](/images/home-lan-normal.png)
*端末のDNSだけをWyse(AdGuardHome)に向け、広告・トラッカーをブロックする。管理はMacからSSH。*

図の線は3種類あります。①の線はDNSの問い合わせで、スマホやMacから真ん中のWyseに届き、Wyseからインターネット上のDNSサーバに転送されます。もう1種類はWebページそのものの通信で、Wyseを通らずにルーター（光BBユニット）から直接インターネットに出ます。②の線は、MacからSSHでWyseを管理する通信です。

つまり、Wyseが関わるのは「どのサーバにつなぐか」を調べる段階だけです。動画や画像などの重い通信はWyseを通らないので、非力な機体でも家全体が遅くなりません。

使っている資源は次のとおりです。メモリは導入直後で77MB、1か月あまり動かした今は約100MBで、2GBのうちのごく一部です。ディスクは導入直後で3.5GBを使い、空きは2.8GBでした。CPUやメモリには余裕がある一方、ディスクの空きは少なめです。

## 仕組み：DNSの段階で広告を止める

### DNSは「名前から住所を調べる仕組み」

スマホでWebサイトを開くとき、端末はまず `example.com` のような名前を、`203.0.113.10` のような数字の住所（IPアドレス）に置き換えます。この置き換えを担当するのがDNSサーバです。電話帳で名前から電話番号を引くのに近い動きです。

広告も同じで、ページの中の広告を表示する前に、端末は広告配信サーバの名前をDNSで調べています。

### AdGuardHomeは広告の名前にだけ「ない」と答える

AdGuardHomeは、家の中に置くDNSサーバのソフトウェアです。広告やトラッカーのドメインの一覧を持っていて、一覧にある名前を聞かれると、どこにもつながらない住所 `0.0.0.0` を返します。端末は広告配信サーバにつながらないので、広告が表示されません。この方式を「DNSシンクホール」と呼びます。

端末側はDNSの問い合わせ先をAdGuardHomeに変えるだけで済みます。アプリを入れられない機器でも、DNSの設定さえ変えられれば効きます。

### 普通のサイトは「上流DNS」に聞いてもらう

広告ではない普通のサイトを開くとき、AdGuardHomeは自分では住所を知らないので、インターネット上の別のDNSサーバに問い合わせて答えを受け取り、端末に返します。この問い合わせ先を「上流DNS」と呼びます。

今回は上流DNSとの通信をDoH（DNS over HTTPS）にしました。DoHは、DNSの問い合わせをWebと同じHTTPSで暗号化して送る方式です。これで、家からどんな名前を問い合わせたかは、回線事業者（ISP）から見えなくなります。

ただし、見えなくなるのはDNSの問い合わせだけです。その後に実際につなぐ相手のIPアドレスや、HTTPSの接続を始めるときに送るサイト名（SNI）は、今までどおり回線事業者から見えます。DoHは通信全体を隠す仕組みではありません。

## なぜこの構成にしたか

**Wyse 3040**：ファンがないので静かで、消費電力も小さく、24時間つけっぱなしに向いています。何より家で余っていました。弱点は、保存領域がeMMC（スマホなどに使われる基板直付けのフラッシュメモリ）の8GBしかないことです。

**Ubuntu Server（minimized）**：画面表示の仕組み（デスクトップ環境）を持たない、最小構成のサーバ版です。DNSサーバに画面は要らず、8GBのディスクに収まるのがこれでした。軽量ディストリのLubuntuで2回インストールに失敗してから、ここに落ち着きました（失敗の話は別の記事にまとめる予定です）。

**AdGuardHome**：1つの実行ファイル（単一バイナリ）で動き、自動更新の仕組みも持っています。同じ目的のPi-holeは複数のソフト（dnsmasq等）を組み合わせて動くので、動かすものが1つで済むAdGuardHomeのほうがこの機体に向いていました。

**Dockerを使わず直接インストール**：Dockerは、ソフトを専用の箱（コンテナ）に入れて動かす仕組みです。今回は使わず、直接インストールしました。理由は、ディスクが8GBしかないうえに、Docker自体にも追加のディスクとメモリが必要だからです。

| | ディスク | メモリ |
|---|---|---|
| 直接インストール | 約40MB | 約50〜100MB（実測77MB） |
| Docker | 約400〜500MB＋イメージ60MB | 上記＋dockerd常駐 100〜200MB |

実測値は直接インストールしたときのメモリ77MBだけで、ほかは見積もりです。空き2.8GB、メモリ2GBの機体では、Dockerのぶんの上乗せが相対的に重くなります。AdGuardHomeは単一バイナリで自動更新も持っているので、コンテナに入れる利点（環境の分離や更新のしやすさ）も小さいと判断しました。

## 構築手順

ここからの作業は、OSを入れたWyseにMacからSSHで接続して行いました。

### 1. タイムゾーンを日本時間にする

初期状態はUTC（世界標準時）なので、そのままだとAdGuardHomeの問い合わせ記録の時刻が9時間ずれます。最初に直しておきます。

```bash
sudo timedatectl set-timezone Asia/Tokyo
```

### 2. AdGuardHomeを取得して配置する

**目的**：AdGuardHomeの実行ファイル一式を `/opt/AdGuardHome` に置きます。

公式は `curl | sh`（ダウンロードしたスクリプトをそのまま実行する方法）を案内しています。今回は、何が置かれるかを自分で把握したかったので、GitHubのリリースから直接取得して手で配置しました。

```bash
URL=$(curl -sL https://api.github.com/repos/AdguardTeam/AdGuardHome/releases/latest \
  | grep -o 'https://[^"]*AdGuardHome_linux_amd64.tar.gz' | head -1)
cd /tmp
curl -sL -o AdGuardHome.tar.gz "$URL"
tar xzf AdGuardHome.tar.gz
sudo mv /tmp/AdGuardHome /opt/AdGuardHome
```

1〜2行目で最新版のダウンロードURLを調べ、残りの行でダウンロード、展開、移動をしています。

**確認**：実行ファイル `AdGuardHome` が置かれていれば成功です。

```bash
ls /opt/AdGuardHome
```

### 3. ポート53を空ける（ここが一番大事）

**何が問題か**：DNSサーバは、決まった受付窓口（ポート53番）で問い合わせを受けます。ところがUbuntuでは、`systemd-resolved` という名前解決の仕組みが最初から53番を使っています。このままではAdGuardHomeが53番を使えません。

**目的**：`systemd-resolved` に53番を手放させつつ、Wyse自身の名前解決は続けられるようにします。

```bash
sudo cp /etc/systemd/resolved.conf /etc/systemd/resolved.conf.bak
echo "DNSStubListener=no" | sudo tee -a /etc/systemd/resolved.conf
sudo ln -sf /run/systemd/resolve/resolv.conf /etc/resolv.conf
sudo systemctl restart systemd-resolved
```

1行目は設定ファイルのバックアップです。2行目の `DNSStubListener=no` で、`systemd-resolved` が53番で待ち受けるのをやめさせます。3行目では、Wyse自身が名前を調べるときの参照先 `/etc/resolv.conf` を、実際の上流DNSが書かれたファイル `/run/systemd/resolve/resolv.conf` に付け替えます。4行目で設定を反映します。

:::message alert
`DNSStubListener=no` **だけ**で終えると、`systemd-resolved` は53番を手放しますが、`/etc/resolv.conf` は `nameserver 127.0.0.53` を指したままになります。そこにはもう誰もいないので、**Wyse自身の名前解決が止まります**。3行目の付け替えまでやって初めて成り立ちます。
:::

**確認**：1行目で53番を使っているプログラムが表示されなければ、53番は空いています。2行目で `github.com` の住所が表示されれば、Wyse自身の名前解決も動いています。

```bash
sudo ss -tulnp | grep ':53 '
getent hosts github.com
```

### 4. サービスとして登録する

**目的**：Wyseを起動したら、AdGuardHomeも自動で動くようにします。

```bash
cd /opt/AdGuardHome
sudo ./AdGuardHome -s install
```

`-s install` を付けると、systemd（Linuxでサービスを管理する仕組み）への登録、自動起動の有効化、起動までを一度にやってくれます。

**確認**：`Active: active (running)` と表示されれば動いています。

```bash
systemctl status AdGuardHome
```

### 5. スリープさせない

**目的**：DNSサーバが眠ると、家中の名前解決が止まります。スリープ系の動作を4つまとめて無効にします。

```bash
sudo systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target
```

`mask` すると、それぞれの動作が `/dev/null`（何もしない特殊なファイル）に付け替えられ、どこから呼ばれても起動しなくなります。何もしないままだと、ACPIイベント（電源まわりのハードウェアからの通知）などから呼ばれる可能性が残ります。

:::message
電源ボタンは無効にしていません（`logind.conf` は初期設定のまま）。物理的に安全に止める手段は残しておきたかったからです。
:::

### 6. 初期設定ウィザードを済ませる

ブラウザで `http://<WyseのIP>:3000` を開くと、AdGuardHomeの初期設定画面が出ます。

| 項目 | 設定値 |
|---|---|
| 管理用ウェブUI | 全インターフェイス / ポート 80 |
| DNSサーバ | 全インターフェイス / ポート 53 |
| 管理者アカウント | 任意 |

設定が終わると、管理画面は `:3000` の付かないURLに変わります。

ここで選んだ「全インターフェイス」は、Wyseが持つすべてのアドレスで受け付ける、という意味です。この選び方には落とし穴があるので、手順8で受け付けるアドレスを絞ります。

:::message alert
管理画面は**家庭内LANだけで使う**前提です。ルーターのポート開放などで**インターネット側に絶対に出さない**でください。管理者パスワードも強いものにします。
:::

### 7. 上流DNSにDoHを設定する

管理画面の上流DNSの欄に、Quad9のDoHのURLを入れました。

```
https://dns10.quad9.net/dns-query
```

:::message
非力な機体では、DoHの暗号化（TLS）の処理が負荷になるかもしれません。測ってはいませんが、体感が重ければ暗号化しない普通のDNSに戻すのも選択肢です。プライバシーと速度のどちらを取るか、の判断になります。
:::

### 8. 受け付けるアドレスを家の中に絞る

**何が問題か**：手順6で選んだ「全インターフェイス」には、IPv6のアドレスも含まれます。IPv4では、家の機器はルーターの内側にあり、外からは直接届きません。一方、IPv6では家の機器一つ一つにインターネットから届くアドレス（グローバルアドレス）が付きます。外から届くかどうかはルーターのIPv6のフィルタ次第で、その既定の動きは機種によって違います。

もし外から届くと、AdGuardHomeはだれでも使えるDNSサーバ（オープンリゾルバ）として、DDoS攻撃の踏み台に使われるおそれがあります。管理画面もインターネットから見えてしまいます。私はこれに1か月あまり気づかずにいました（経緯は[後編](https://zenn.dev/yowahada/articles/wyse-adguardhome-home-dns-2)に書きます）。

**目的**：家の端末はIPv4でWyseを指定するので、IPv6で受け付ける必要はありません。受け付けるアドレスを、WyseのIPv4アドレスとWyse自身（`127.0.0.1`）だけにします。設定ファイル `/opt/AdGuardHome/AdGuardHome.yaml` の2か所を、バックアップを取ってから書き換えます。

```yaml
# DNSを受け付けるアドレス（dns: の中）
  bind_hosts:
    - 127.0.0.1
    - <WyseのIP>

# 管理画面のアドレス（http: の中）
  address: <WyseのIP>:80
```

`127.0.0.1` を残したのは、後編で書く毎朝の点検が、Wyseの中から `127.0.0.1` のDNSに問い合わせて動作を確かめているからです。

書き換えたら `sudo systemctl restart AdGuardHome` で再起動します。再起動の数秒間は、家の名前解決が止まります。

**確認**：53番と80番の行に、IPv4のアドレスだけが並べば成功です。`*:53` や `[::]:53` のような、すべてのアドレスを表す行が残っていなければ大丈夫です。

```bash
sudo ss -tulnp | grep AdGuardHome
```

:::message alert
IPv6が使える回線では、「ルーターの内側だから外から届かない」という前提は成り立たないことがあります。家の中に置くサーバも、受け付けるアドレスを最初から必要な範囲に絞っておきます。
:::

## 動いているか確かめる

ここまでで、WyseはDNSサーバとして動いています。Macなど別の端末から、Wyseに直接問い合わせて確かめます。`doubleclick.net` は広告配信で使われるドメインの1つです。

```bash
nslookup doubleclick.net <WyseのIP>
```

答えの住所が `0.0.0.0` なら、AdGuardHomeが広告のドメインを止めています。普通のサイト（たとえば `github.com`）を同じように聞いて、本物の住所が返れば、上流DNSへの転送も動いています。

## まとめ（前編）

- **ポート53を空けるときは、`/etc/resolv.conf` の付け替えまでやります。** `systemd-resolved` を止めるだけだと、Wyse自身の名前解決が止まります。
- **DoHで隠れるのはDNSの問い合わせだけです。** つなぐ相手のIPアドレスやサイト名は、今までどおり回線事業者から見えます。
- **受け付けるアドレスは、最初から家の中に絞ります。** 「全インターフェイス」のままだと、IPv6で家の外から届くことがあります。

[後編](https://zenn.dev/yowahada/articles/wyse-adguardhome-home-dns-2)では、このDNSサーバを家のスマホやPCに使ってもらい、毎朝の点検を組みます。
